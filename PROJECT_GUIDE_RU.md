# Подробный гид по проекту простыми словами

Здесь объясняется, что задано, зачем нужна каждая часть, как данные проходят обработку и как самому проверить результат. Для быстрого запуска переходи к разделу 10. Для понимания и подготовки к защите читай по порядку.

## 1. Что нужно было сделать

По твоему запросу выполнены D1, D2 и Data Engineering Capstone из tasks.txt. C1/C2, Cybersecurity Capstone и упражнения W1–W20 не входят в выбранный тобой объём.

В начале задания описаны уровни: Core обязателен, Advanced нужен для высшей оценки, Challenge даёт бонусы. В проекте оставлены все уровни. Некоторые возможности Advanced/Challenge отдельно требуются итоговой программе.

Основные правила: Python 3.11+, стандартная библиотека, pytest для тестов, выходные даты в UTC. Неправильная запись должна учитываться и отклоняться с причиной, позволяя обработать остальные.

## 2. Общая идея на примере магазина

Представь, что магазин каждый день получает файлы с заказами. В них могут быть неверные суммы, неполные email, разные форматы телефонов, даты разных часовых поясов и повторы заказов. Файлы могут приходить с опозданием, а источник — временно не отвечать.

Программа должна прочитать доступные записи, привести их к одному виду, сохранить результат и объяснить, что было отклонено.

Это называется **ETL**:

1. Extract — прочитать данные.
2. Transform — преобразовать и проверить записи.
3. Load — сохранить результат.

После загрузки итоговый проект дополнительно проверяет качество всего подтверждённого набора: например, нет ли повторных ID в разных файлах.

```text
Входные файлы
      ↓
Чтение записей
      ↓
Проверка и преобразование
      ├── ошибка записи → карантин с причиной
      ├── фильтр/повтор → намеренный пропуск
      └── подходящая запись → сохранение по UTC-дате
                                      ↓
                         Проверка качества набора
                                      ↓
                                Отчёт запуска
```

**Запись** — одна строка заказа или одно событие клика. В Python это обычно словарь: `{"order_id": "1000", "amount": "120.50"}`. order_id и amount — имена полей, справа находятся значения.

### Что делает common.py

В нём всего три общие вспомогательные функции:

- utc_now возвращает текущее время в UTC в виде строки для отчётов и состояния.
- json_default объясняет JSON-записи, как сохранить дополнительные типы: Decimal становится строкой, дата — строкой UTC. Без этого обычный JSON-сериализатор не понимает Decimal.
- atomic_json сначала полностью записывает временный JSON и затем заменяет им готовый файл. Это используется, например, для watermark, чтобы при прерывании не оставлять наполовину записанный JSON.

Сами алгоритмы заданий находятся в их solution.py; common.py только помогает сохранять данные одинаковым способом.

### Небольшие файлы настроек

requirements-dev.txt перечисляет pytest для установки тестов. Для обычной обработки заказов сторонние библиотеки не нужны.

pytest.ini указывает папки тестов и способ импортов: в разных заданиях повторяются имена solution.py и test_solution.py, но pytest должен различать их по папкам.

.gitignore ничего не удаляет. Он лишь говорит Git не включать локальный Python, кэш и результаты work в обычный список новых файлов для сохранения в репозитории. Сам запуск программы и появление результатов от этого не блокируются.

## 4. Что происходит при запуске команды

```powershell
.\.tools\python311\python.exe -B -m minietl capstone/configs/orders.json
```

| Часть команды | Значение |
|---|---|
| .\.tools\python311\python.exe | Какой Python запустить. |
| -B | Не создавать файлы кэша .pyc; на обработку данных это не влияет. |
| -m minietl | Запустить модуль minietl из проекта. |
| capstone/configs/orders.json | Использовать настройки заказов из этого JSON. |

В minietl.py находится короткий вызов main из capstone/solution.py. Большая логика расположена именно в capstone/solution.py. Такое разделение позволяет использовать её и через команду, и в тестах.

**solution.py отдельного упражнения часто только определяет функции и классы.** Если запустить такой файл и не увидеть результата, это само по себе не ошибка. Упражнения проверяют тестами или вызовом нужной функции из Python; примеры есть в разделе 13.

Все команды этого гида выполняются из корня проекта — папки, где находятся tasks.txt и minietl.py.

## 5. Какие форматы данных используются

**CSV** — таблица в текстовом файле. Первая строка задаёт имена столбцов:

```csv
order_id,customer_email,phone,amount,currency,order_date
1001,aru@example.com,+7 701 123 4567,120.50,USD,2026-10-01
```

Модуль csv понимает разделители и кавычки. Просто делить строку по запятой было бы ненадёжно: запятая может находиться внутри значения в кавычках.

**JSON** хранит данные с именами полей. Он используется для конфигов, отчётов и состояния.

**JSONL** — отдельный JSON-объект на каждой строке:

```json
{"order_id": "1001", "amount": "120.50"}
{"order_id": "1002", "amount": "99.00"}
```

Это не один большой JSON-массив. Программа читает строки отдельно: повреждённая строка не мешает прочитать следующую.

**UTF-8** — кодировка: правило превращения байтов файла в буквы. Основная кодировка проекта — UTF-8. В D1.1 есть резервная cp1251 по условию. Повреждённые UTF-8 строки JSONL учитываются и пропускаются. CSV с UTF-8 BOM, небольшой отметкой перед заголовком Windows-файлов, тоже поддерживается.

## 6. Как работает каждое задание D1

### D1.1 — CSV и карантин

Код: [d1/d1_1_csv_ingestion/solution.py](d1/d1_1_csv_ingestion/solution.py).

Главная функция ingest:

1. Читает UTF-8; при ошибке один раз пробует резервную кодировку.
2. Проверяет заголовок.
3. Для каждой записи проверяет заполненность полей, сумму и повтор order_id.
4. Хорошую запись пишет в clean.csv, плохую — в rejects.csv с причиной.
5. Выводит статистику.

Ошибки различаются по именам: MissingField — отсутствует значение, InvalidAmount — неправильная сумма, DuplicateKey — уже принят такой ID, InvalidCSV — строка не разбирается как CSV. Все они относятся к ValidationError, общей ошибке проверки.

**Карантин** — отдельное место для неправильных записей, чтобы позже можно было разобраться и исправить источник. Исходный файл при этом не удаляется.

Если сам CSV-парсер не смог получить поля, например из-за слишком длинного значения, rejects.csv содержит причину с номером строки, а поля остаются пустыми. После ошибки обработка следующих записей продолжается.

В D1.1 email проверяется на наличие, а не на формат: по условию строка 1002 должна пройти этот этап. Исходный пример даёт 2 принятые и 3 отклонённые строки.

Для суммы используется **Decimal** — десятичное число для точной работы с деньгами, например Decimal("120.50"). Ноль здесь допустим, отрицательные и неконечные значения — нет.

### D1.2 — единое время и папки по датам

Код: [d1/d1_2_dates/solution.py](d1/d1_2_dates/solution.py).

normalise_ts принимает поддерживаемые форматы и переводит время в UTC. UTC — общая точка отсчёта времени, чтобы одинаково сравнивать события разных источников.

Если зона не указана, используется source_tz — пояс источника. Если в самой дате уже есть смещение вроде +02:00, учитывается именно оно.

```text
Вход:     2026-11-01T01:30:00, источник Asia/Tokyo
Результат:2026-10-31T16:30:00+00:00
Папка:    year=2026/month=10/day=31
```

+00:00 означает UTC; T отделяет дату от времени. Локально уже ноябрь, но в UTC ещё октябрь.

**Партиция** здесь — обычная папка для записей одной даты. partition_path вычисляет имя, write_partitions сохраняет записи по папкам.

01/10/2026 неоднозначна: dayfirst=True означает 1 октября, False — 10 января. Программа не угадывает намерение автора. Невозможная дата, например 2026-13-01, вызывает InvalidDate с исходным значением.

### D1.3 — очистка текста и маскирование

Код: [d1/d1_3_text_cleaning/solution.py](d1/d1_3_text_cleaning/solution.py).

normalise_phone убирает лишние символы, заменяет ведущую 8 на 7, при необходимости добавляет 7 к десятизначному номеру и расставляет разделители:

```text
8(701)1234568 → +7-701-123-4568
```

validate_email проверяет адрес практичным шаблоном. **Регулярное выражение** — правило допустимого вида строки; fullmatch проверяет всю строку. Это проверка формы, а не существования почтового ящика.

Маскирование скрывает часть личных данных:

```text
aru@example.com → a***@example.com
+7-701-123-4567 → ***-***-4567
```

strip_html превращает простое <b>Book</b> в Book. Это подходит для доверенных простых описаний, но не заменяет HTML-парсер и защиту от опасного содержимого.

analytics_export объединяет действия в отдельном экспорте. Обычный orders.json нормализует email/телефон, но автоматически их не маскирует.

### D1.4 — только новые ежедневные файлы

Код: [d1/d1_4_incremental/solution.py](d1/d1_4_incremental/solution.py).

IncrementalLoader ищет events_YYYY-MM-DD.jsonl, извлекает дату из имени и берёт даты новее сохранённой. Неподходящие имена журналируются.

**Watermark** — сохранённая отметка прогресса. Здесь это последняя успешно обработанная дата файла.

Строки JSONL читаются по одной. Ошибки JSON, кодировки и чрезмерной вложенности учитываются и пропускаются. Для хорошей записи вызывается переданная функция process.

Если process аварийно завершилась, файл не подтверждается: watermark этого файла остаётся прежним. Сам callback должен позаботиться о повторяемости своих побочных действий при повторе.

Состояние записывается после полного файла: сначала временный JSON, затем он заменяет готовый. Это помогает избежать наполовину записанного JSON.

Простой загрузчик не принимает старые поздние файлы. В capstone учёт расширен до отдельных файлов, поэтому поздние поступления там поддерживаются.

### D1.5 — повтор временно неудачного вызова

Код: [d1/d1_5_retry/solution.py](d1/d1_5_retry/solution.py).

retry — обёртка функции: после ConnectionError/TimeoutError подождать и попробовать снова. Задержка растёт, к ней добавляется небольшая случайная часть — jitter.

Например, без jitter при base=1 задержки будут 1, 2, 4 секунды и т. д. max_attempts включает первый вызов. ValueError не повторяется: неверные параметры от ожидания не исправятся.

После исчерпания попыток RetryExhausted сообщает их число и затраченное время, сохраняя исходную причину. Тесты подменяют настоящее ожидание, поэтому выполняются быстро.

В файле есть демонстрационная flaky_source, которая специально случайно выдаёт ошибки. Она показывает смысл повторов и не вызывается автоматически при запуске конфигов orders.json/clicks.json. Обычные примеры читают локальные файлы и не получают случайных сбоев из-за этой демонстрации.

### D1.6 — сессии кликов

Код: [d1/d1_6_sessions/solution.py](d1/d1_6_sessions/solution.py).

**Сессия** — последовательность посещений пользователя без большого перерыва:

```text
10:00, 10:10, 10:40 → одна сессия, три страницы
11:11              → новая сессия
```

Ровно 30 минут остаются в одной сессии; новая начинается при большем перерыве. Полночь сама по себе сессию не разрывает.

sessionise приводит события к UTC, сортирует по пользователю/времени и считает начало, конец, длительность и страницы. Неверные события попадают в rejects. sessionise_file читает JSONL и пишет CSV с сессиями.

Конфиг clicks.json только очищает и загружает события; сессии вызываются отдельно.

## 7. Как работает каждое задание D2

### D2.1 — объект заказа Order

Код: [d2/d2_1_order_model/solution.py](d2/d2_1_order_model/solution.py).

**Класс** — описание того, каким должен быть объект. Order описывает заказ с ID, email, суммой, валютой и временем.

Это dataclass: Python помогает создать класс для хранения полей. frozen=True запрещает обычное изменение полей после создания.

При создании проверяются положительный ID, email, сумма строго больше нуля, валюта из трёх заглавных букв и дата с часовым поясом. Время приводится к UTC.

from_row создаёт Order из словаря со строками; to_row возвращает строки для сохранения. Если заказ сохранить в таком представлении и прочитать обратно, получится равный ему объект.

Основной Pipeline передаёт словари и не создаёт Order автоматически. Встроенная схема Cast с именем orders преобразует ID и сумму, но сама по себе не выполняет все проверки модели Order.

### D2.2 — откуда читать и куда писать

Код: [d2/d2_2_sources_sinks/solution.py](d2/d2_2_sources_sinks/solution.py).

**Source — источник**, **Sink — приёмник**.

| Класс | Что делает |
|---|---|
| CsvSource | Читает CSV. |
| JsonLinesSource | Читает JSONL по строкам. |
| InMemorySource | Берёт записи из переданной коллекции в памяти; удобен в тестах. |
| CsvSink | Сохраняет CSV. |
| JsonLinesSink | Сохраняет JSONL. |
| InMemorySink | Складывает записи в память; удобен для проверки результата. |
| PartitionedSink | Распределяет записи по папкам UTC-даты. |

Source и Sink задают общие правила; для работы создаётся конкретный CsvSource, JsonLinesSink и т. п.

read выдаёт записи постепенно — не нужно загружать весь большой файл в память. write принимает записи и возвращает число принятых.

Общий Connector отвечает за with: открыть ресурс при входе и закрыть при выходе, включая выход после ошибки. Это помогает не забыть закрыть файл.

Матрица 3 × 3 в тестах — все девять сочетаний трёх основных источников и трёх приёмников.

### D2.3 — действия над записью и Pipeline

Код: [d2/d2_3_transforms/solution.py](d2/d2_3_transforms/solution.py).

**Transform** — одно действие над записью:

| Действие | Пример |
|---|---|
| Filter | Оставить оплаченные заказы. |
| Rename | Переименовать customer_email в email. |
| Cast | Превратить ID из строки в число, проверить сумму. |
| Deduplicate | Убрать повторный ключ. |
| NormaliseDate | Привести поле времени к UTC. |
| TransformChain | Объединить несколько действий в одно. |

apply возвращает новый словарь или None. None означает «эту запись намеренно пропустить». Ошибка действия попадает в rejects с сообщением, обработка следующей записи продолжается.

Pipeline соединяет источник, действия и приёмник. Оператор | позволяет записать цепочку слева направо:

```python
source | Cast({'id': int}) | Deduplicate('id')
```

into(sink) запускает цепочку. PipelineStats содержит входные, выходные, отклонённые и намеренно пропущенные записи, причины и счётчики шагов.

Deduplicate хранит встреченные ключи между записями; в начале нового исполнения Pipeline состояние сбрасывается.

Pipeline.into сам не запускает QualitySuite. Проверки качества вызываются отдельно; в итоговом CLI они запускаются автоматически после загрузки.

### D2.4 — качество целого набора

Код: [d2/d2_4_quality/solution.py](d2/d2_4_quality/solution.py).

Даже если отдельные записи подходят, весь набор может иметь проблему: например, одинаковый ID в разных файлах.

| Проверка | Что ищет |
|---|---|
| NotNull | Поле отсутствует, равно None или пустой строке. |
| Unique | Отсутствующие или повторные значения. |
| InRange | Выход за включённые нижнюю/верхнюю границы. |
| MatchesPattern | Строка целиком не соответствует шаблону. |
| Freshness | Дата слишком старая, неверная или будущая. |

Каждая возвращает CheckResult: имя, успешность, число нарушений, до пяти примеров и уровень severity.

QualitySuite — набор таких проверок с общим запуском и отчётом. Error делает итог качества неуспешным; warning сообщает, но сам по себе не проваливает запуск.

QualitySuite.run сохраняет входные записи в список для повторного обхода. Для сохранённых данных capstone использует run_factory: каждая проверка заново читает данные с диска, без списка всех записей.

### D2.5 — одинаковые обещания всех приёмников

Код: [d2/d2_5_lsp/solution.py](d2/d2_5_lsp/solution.py).

Все Sink обещают принимать любой набор, включая пустой, возвращать число и поддерживать flush.

- BatchSink принимает даже одну запись и временно складывает в буфер. При накоплении порции или flush/close буфер переносится дальше. Возвращённое число означает приём записей; завершение буферизации наступает позже.
- DryRunSink только считает записи без сохранения результата.
- WarehouseSink — учебная модель хранилища в памяти без настоящей БД, с работающим flush.

Flush означает «завершить отложенную отправку/запись», если она есть. У приёмника без отложенной работы это действие может ничего не делать.

LSP — принцип: разновидность объекта должна сохранять обещания базового типа. Здесь для понимания достаточно примеров приёмников выше. Общие тесты проверяют эти обещания для всех Sink.

### D2.6 — сборка программы по JSON

Код: [d2/d2_6_registry/solution.py](d2/d2_6_registry/solution.py).

**Конфиг** — файл настроек. **Реестр** — словарь, связывающий короткое имя с нужным классом.

```json
{"type": "dedupe", "key": "order_id"}
```

По имени dedupe выбирается Deduplicate, а order_id задаёт поле поиска повторов.

__init_subclass__ заполняет реестр при определении именованного подкласса. Не нужно дописывать длинный выбор «если csv, иначе если jsonl...» при каждом новом компоненте.

construct создаёт компонент; build_pipeline собирает цепочку. Неизвестный тип или отсутствующий параметр даёт ConfigError с местом ошибки. transforms[1].key — поле key у второго преобразования: счёт в Python начинается с нуля.

JSON выбирает только разрешённые конвертеры и именованные фильтры, произвольный Python-код из настроек не выполняется.

## 8. Путь одного заказа через capstone

Код: [capstone/solution.py](capstone/solution.py). Возьмём такую запись:

```json
{
  "order_id": "1000",
  "email": "aru@example.com",
  "phone": "+7 701 123 4567",
  "amount": "120.50",
  "currency": "USD",
  "ordered_at": "2026-10-26T23:30:00",
  "product_description": "<b>Book</b>"
}
```

По настройкам orders.json:

1. JsonLinesSource получает из строки Python-словарь.
2. Cast превращает ID в int, проверяет Decimal-сумму и email, нормализует телефон, убирает простые теги описания.
3. Преобразование date понимает наивное время как Tokyo и переводит в UTC.
4. Deduplicate проверяет, не встречался ли ID в этом входном файле.
5. Вычисляется папка UTC-даты.
6. Приёмник пишет результат во временную папку.
7. После полного файла результат публикуется и файл подтверждается в watermark.

Результат; порядок полей не важен:

```json
{
  "order_id": 1000,
  "email": "aru@example.com",
  "phone": "+7-701-123-4567",
  "amount": "120.50",
  "currency": "USD",
  "ordered_at": "2026-10-26T14:30:00+00:00",
  "product_description": "Book"
}
```

Сумма во время обработки — Decimal, а в JSON становится строкой для сохранения десятичной точности. ID стал числом, телефон и описание очищены, дата переведена в UTC.

Если amount равна abc или email неверен, запись пойдёт в карантин. Если это повтор ID, она будет учтена как dropped. Другие записи продолжат обрабатываться.

После всех новых файлов проверяется качество всего подтверждённого набора и формируется отчёт.

### Как читать конфиг

Файлы находятся в capstone/configs/.

| Раздел | Что задаёт в примере заказов |
|---|---|
| source | JSONL из examples/data/orders/. Звёздочка — все подходящие имена. |
| transforms | Поля и преобразования по порядку. |
| checks | Наличие email, уникальность ID, валюту из трёх заглавных букв. |
| sink | JSONL-выход в work/orders/output/. |
| partition | Поле ordered_at для папок; наивное время источника — Tokyo. |
| incremental | Где хранить прогресс, отчёт, карантин. |
| retry | Число попыток и задержки временных ошибок. |

Пути внутри JSON считаются **от папки самого конфига**. ../examples означает: выйти из configs на уровень capstone, затем зайти в examples. Это не путь от текущей папки терминала.

У кликов поле времени — timestamp, проверки относятся к user_id/url.

Если изменить source/transforms/sink/partition при старом watermark, программа попросит новые пути watermark и output, чтобы не смешивать результаты разных правил. Checks и retry разрешается менять без повторной загрузки.

### Почему повтор не загружает всё заново

Для каждого файла сохраняются путь, SHA-256 — отпечаток содержимого для сравнения версии — и ссылки на результат. Неизменённый файл пропускается. Новый обрабатывается. Изменённый заменяет свои результаты. Переименование меняет путь и считается другим источником для этого учёта.

**Идемпотентность загрузки** — повтор тех же файлов не создаёт лишних строк из-за самого повторного запуска.

Это отличается от повторных заказов внутри входных данных. Deduplicate действует внутри файла. Unique обнаруживает одинаковые ID между файлами, но сам записи не удаляет.

Поздний новый файл со старой датой принимается: capstone учитывает файлы отдельно, а не только максимальную дату.

Watermark подтверждает загрузку, качество проверяется после неё. Провал проверки не откатывает подтверждённые файлы. При следующем запуске весь набор проверится снова, даже без новых файлов.

При временной ошибке повторяется приватная обработка файла, без публикации частичной попытки. После сбоя публикации повтор использует те же выходные имена, помогая не создавать дубликаты.

## 9. Где результат и как читать отчёт

```text
capstone/work/orders/
├── output/year=2026/month=10/day=26/...-records.jsonl
├── watermark.json
├── rejects.jsonl
├── report.json
└── watermark_batches/
```

| Место | Что смотреть |
|---|---|
| output | Очищенные записи по UTC-датам. |
| rejects.jsonl | Запись, причина, шаг, файл; ошибки источника — также номер строки. Для неразобранного CSV вместо полей может быть только диагностическая причина. |
| watermark.json | Подтверждённые версии входных файлов. Обычно вручную не редактируется. |
| report.json | Итоги последнего запуска и проверки качества. |
| watermark_batches | Внутренние данные для качества и восстановления. Для обычного просмотра достаточно output, rejects и report. |

Для кликов — аналогичные файлы внутри capstone/work/clicks/. Длинный идентификатор в имени выходного файла связан с исходным путём; вручную его задавать или расшифровывать не нужно.

| Поле отчёта | Значение |
|---|---|
| status | success — успешный запуск; failed — неуспешный. |
| start/end | UTC-время начала/конца. |
| duration_seconds | Длительность в секундах. |
| files_processed | Обработанные новые/изменённые файлы. |
| files_skipped | Пропущенные неизменённые файлы. |
| rows_in | Прочитанные записи текущей загрузки, включая ошибочные. |
| rows_out | Принятые записи текущей загрузки. |
| rejected | Отклонённые из-за ошибок. |
| dropped | Намеренные пропуски, например повторы. |
| steps | Счётчики отдельных действий. Их не надо складывать: одна запись проходит несколько действий. |
| checks | Результаты качества. |
| quality_rows | Размер всего подтверждённого набора, который проверялся. |

Для примеров без аварий обычно rows_in = rows_out + rejected + dropped.

При повторе rows_out может быть 0, а quality_rows — 14: новых заказов нет, но 14 сохранённых проверены снова. Карантин при этом сохраняет прежние причины, хотя rejected текущего запуска равен нулю.

Отчёт относится к **последнему** запуску. Второй запуск заменит report.json данными повтора.

Success не означает отсутствие плохих входных строк: rejected может быть больше нуля, если ошибки учтены, хорошие записи загружены и настроенные проверки результата пройдены.

## 12. Как понять сообщение об ошибке

| Что увидел | Объяснение и действие |
|---|---|
| Python не найден или открывается Microsoft Store | Используй .\.tools\python311\python.exe. |
| Не найден minietl, d1 или d2 | Проверь папку терминала и полноту скопированного проекта. Запуск нужен из корня. |
| No module named pytest | У выбранного интерпретатора нет pytest. На другом компьютере установи requirements-dev.txt тем же Python, которым запускаешь тесты. |
| Success, но rows_out 0 | Возможно, всё уже загружено. Посмотри files_skipped/quality_rows; для чистого запуска используй раздел 11. |
| Rejected больше нуля при success | Плохие записи учтены, хорошие загружены. Для предоставленных примеров это нормально. |
| Failed и в checks есть нарушение severity error | Не пройдена проверка качества набора. Посмотри failed_count и sample_failures. Warning сам по себе запуск не проваливает. |
| ConfigError с transforms[1].key | Проблема поля key во втором преобразовании; открой конфиг. |
| pipeline changed | Правила обработки изменены при старом состоянии. Нужны новые watermark/output, проще отдельная копия. |
| invalid JSON в watermark | Состояние повреждено. Не подменяй его пустым JSON. Для демонстрации возьми чистую копию, сохранив прежние данные для разбора. |
| RetryExhausted | Временная ошибка повторялась слишком много раз. Посмотри исходную причину и источник; ожидание не исправляет неверный формат. |
| FileNotFoundError в JSON-сообщении CLI | Проверь путь к конфигу/входу. Пути внутри конфига считаются от самого JSON. |
| FAILED/ERROR у pytest | Проверка реально не прошла. Посмотри имя теста и различие результатов, запусти группу с -v. |

**Ошибка записи отличается от ошибки запуска.** Неверный email должен попасть в карантин. Отсутствующий конфиг, недоступный диск или error-провал качества должны дать неуспешный запуск с сообщением: скрывать их под success неправильно.

Часть ошибок конфигурации возникает до начала загрузки, поэтому новый полный report.json может не появиться. В таком случае ориентируйся на сообщение CLI и код завершения, а не на оставшийся отчёт предыдущего запуска.

Первая 1 прошла. Bad нельзя превратить в число — rejected. Вторая 1 — повтор, это dropped. Затем прошла 2. Четыре входа, два выхода, одна ошибка и один намеренный пропуск.

### Пример E: качество error и warning

```python
from d2.d2_4_quality.solution import QualitySuite, NotNull
rows = [{'email': 'aru@example.com'}, {'email': ''}]
print(QualitySuite([NotNull('email')]).run(rows)['passed'])
print(QualitySuite([NotNull('email', severity='warning')]).run(rows)['passed'])
```

Ожидается False, затем True. Нарушение есть в обоих случаях, но warning не делает весь результат неуспешным. Чтобы увидеть нарушение, выведи весь словарь результата, а не только passed.

## 14. Несколько важных границ учебного проекта

- Один процесс пишет в конкретный watermark. Два одновременных писателя не поддерживаются.
- Публикация нескольких файлов не является одной общей операцией. После сбоя часть результата может быть видна до повторного запуска и восстановления.
- Источники D2 читают постепенно, но некоторые алгоритмы хранят данные: D1.1 — весь декодированный CSV, сессии — события для сортировки, Deduplicate/Unique — ключи.
- Качество проверяется после загрузки и не откатывает подтверждённые данные.
- Удаление входного файла не удаляет ранее загруженные записи. Старые внутренние поколения автоматически не очищаются.
- CLI рассчитан на файловые коннекторы; InMemory используется в отдельных Pipeline и тестах.
- Отдельных provided-файлов в исходной папке не было, поэтому синтетические примеры созданы для этой работы.

## 15. Что полезно рассказать на защите

Можно объяснить последовательно:

1. «Я читаю заказы/клики, проверяю записи и сохраняю причины ошибок отдельно».
2. «Для денег использую Decimal, даты привожу к UTC для одинакового сравнения и выбора папок».
3. «Source, Transform и Sink разделяют чтение, изменение и запись, Pipeline их соединяет».
4. «JSON выбирает зарегистрированные классы по коротким именам».
5. «Watermark запоминает файлы, поэтому повтор не добавляет данные заново».
6. «QualitySuite проверяет весь подтверждённый набор: error проваливает запуск, warning сообщает».
7. «Тесты проверяют хорошие записи, ошибки, повторы и сбои».

Термины простыми словами:

- **Наследование:** CsvSource — разновидность Source с теми же обещаниями.
- **Композиция:** Pipeline содержит источник, действия и приёмник.
- **Полиморфизм:** QualitySuite вызывает один run у разных Check.
- **Контрактный тест:** общая проверка обещаний применяется к разным классам, например к каждому Sink.
- **Интеграционный тест:** проверяется совместная работа, например загрузка с повреждёнными строками и восстановлением.

Сдавать нужно всю папку проекта с сохранением структуры. Реализации находятся в solution.py каждого задания, но по условию часть заданий переиспользует предыдущие. Один отдельно скопированный файл может не найти нужные импорты.
